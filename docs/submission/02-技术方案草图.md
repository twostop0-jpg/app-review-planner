# 阶段2 技术方案草图

项目：App Review Planner  
仓库：https://github.com/twostop0-jpg/app-review-planner

## 1. 方案目标
在需求拆解基础上，明确模块边界、关键流程、技术取舍与风险。

## 2. 模块边界

| 模块 | 职责 | 边界 |
|------|------|------|
| Web UI | 表单、轮询、结果展示 | 不承载业务算法 |
| Jobs API | 创建/查询任务 | 不直接调模型细节 |
| Pipeline | 七阶段编排与状态更新 | 不持久化到外部 DB（内存 store） |
| collect/clean | 采集与清洗 | 规则驱动，不调 LLM |
| analyze/plan/testcases | 语义生成 | Moonshot + 后端校验 |
| validate | 追溯校验 | 纯规则 |
| moonshot_client | 模型调用/JSON 修复/429 退避 | 不感知业务字段语义 |

## 3. 总体架构草图

```text
用户 → 产品UI(/) 或 Swagger
        ↓
     FastAPI (/api/jobs)
        ↓
   Pipeline 后台线程
   scope → collect → clean → analyze → plan → testcases → validate
                              ↑         ↑         ↑
                         Moonshot   Moonshot   Moonshot
        ↓
   内存 Job Store → UI 轮询展示 artifacts
```

## 4. 关键流程说明
1. `POST /api/jobs` 创建任务，立即返回 `job_id`
2. 后台按阶段推进，每阶段更新 `stages` 与 `artifacts`
3. analyze/plan/testcases 调用 Moonshot 获取 JSON，后端校验 ID 合法性
4. 模型失败或 429：重试/退避；仍失败则规则 fallback（仍保留证据链接）
5. validate 做全链路确定性检查
6. 前端每秒轮询直到 succeeded/failed

## 5. 技术取舍

| 决策 | 选择 | 原因 |
|------|------|------|
| 主 UI | FastAPI 托管页面 | 无需 Node，降低运行门槛 |
| 采集 | RSS XML 优先 + MZStore 回退 | 非页面可见区爬取；结构化更好 |
| 语义阶段 | Moonshot | 满足模型驱动要求 |
| 校验 | 后端规则强校验 | 降低幻觉与断链 |
| 存储 | 内存 Job | 作业演示足够，实现简单 |

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 美区网络/RSS 波动 | live 采不到 | sample/import；透明写 limitations |
| Moonshot 429/坏 JSON | 阶段失败 | 重试、阶段间隔、fallback |
| 证据幻觉 | 结论不可信 | ID allow-list；拒绝无证据项 |
| 端口占用(Win 10013) | 服务起不来 | 使用 8001 |

## 7. 可行性结论
模块边界清晰，关键路径可本地复现；语义能力与规则校验分离，满足作业“模型驱动 + 可追溯”要求。
